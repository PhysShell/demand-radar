# Independent review guide

You are reviewing one candidate opportunity at a time. For each `<opp_id>/`
directory:

- `opportunity.json` — the full card as the analyst produced it (problem,
  persona, evidence counts, proposed wedges, the analyst's own risk list).
- `evidence.jsonl` — every evidence record the card cites, verbatim, one
  JSON object per line. Read the *primary* evidence, not just the card's
  summary of it.
- `review-template.json` — fill this in and return it. Do not submit it
  unedited: every review-required field starts blank/false on purpose.

## What you are here to do

**Look for reasons to reject, not ways to improve the pitch.** This is the
same instruction given to an automated critic
(schemas/critic-verdict.schema.json): find the objection that would make
this a bad experiment to run, not a better wedge or a punchier framing. If
you cannot find a real, evidence-grounded objection, say so plainly
(`objections: []`, a status recommendation, and notes explaining why) —
do not manufacture one to seem thorough, and do not soften a real one to
seem agreeable.

## Filling in review-template.json

- `reviewer.id`: a stable handle that does not itself carry PII.
- `reviewer.conflict`: state it plainly. `"none"` if there truly is none,
  `"product_owner"` if you are the product owner reviewing your own
  candidate. That is allowed, but it is not market validation, and the
  final report will say so.
- `reviewed_at`: ISO-8601 UTC timestamp of when you actually did this.
- `opportunity_hash` / `evidence_manifest_hash`: already filled in — leave
  them exactly as they are. They prove you reviewed *this* version of the
  card and evidence, not an earlier or later one; import rejects a stale
  or tampered hash.
- `attestation.reviewed_primary_evidence`: true only if you actually read
  evidence.jsonl, not just opportunity.json's summary of it.
- `attestation.review_not_generated_by_analyst_provider`: true only if
  this review is genuinely yours, not generated by prompting an LLM
  (including the analyst's own provider) to produce it on your behalf.
- `verdict.recommended_status`: `experiment_ready` | `investigate` |
  `rejected` — a recommendation. The deterministic judge has final say,
  taking your objections (especially any marked `fatal`) as one input.
- `verdict.objections[].evidence_ids`: must reference evidence IDs that
  are actually in this card's `evidence.jsonl` — an objection citing
  evidence from a different card is rejected on import.

## What happens after you submit

Completed `review-template.json` files are collected into one JSONL file
and imported via `demand-radar review import`. Import is atomic: if any
envelope in the batch is invalid (stale hash, wrong run, evidence outside
the card, missing attestation, duplicate review, etc.), the whole batch is
rejected and nothing is written — you will be told which envelope and why.
